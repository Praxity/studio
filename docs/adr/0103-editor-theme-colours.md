# Editor themes and panel accessibility

## Status

Accepted. Existing behaviour recorded during comment removal.

## Context

Course colours, editor chrome and accessible foregrounds have different owners. Substituting raw fills for corrected foregrounds can make controls or text illegible.

## Decision

- `packages/editor-core/src/components/audit/audit-confirm-dialog.tsx`, `AuditConfirmDialog`: The destructive fill is `--status-error`, not the accent, so the label comes from the critical severity pair rather than the accent-text default applied to filled buttons.
- `packages/editor-core/src/components/audit/audit-issue-card.tsx`, `AuditIssueCard`: Was `--praxity-editor-*`, a hardcoded One-Dark/One-Light palette scoped to `[data-editor-theme]`. The desktop app never sets that attribute, so every one of these resolved to nothing: the cards had no border and no surface, and the visited/dismissed states were invisible. `--panel-*` cascades from the active desktop theme.
- `packages/editor-core/src/components/audit/audit-issue-card.tsx`, `AuditIssueCard`: White failed on the lighter severity fills; the badge text is now derived alongside the badge background.
- `packages/editor-core/src/components/design-system-panel.module.css`, `.customModeBadge`: Size the uppercase badge with `--mantine-font-size-xs`, weight 700, and use the corrected foreground token `--panel-accent-text` rather than the raw accent fill. The separate `.customModeText` rule uses the same size token with weight 500 and `--panel-text-muted`. Source: these two selectors in the named stylesheet.
- `packages/editor-core/src/components/design-system-panel.module.css`, `.contrastReadout[data-state="fail"]`: Colour is redundant here: the wording and the icon already carry the verdict (WCAG 1.4.1). --panel-text-secondary is guaranteed 4.5:1 on both the panel and the primary surface in every theme.
- `packages/editor-core/src/components/design-system-panel.module.css`, `.contrastReadout[data-state="fail"]`: --mantine-color-error, not --status-error: the theme's raw statusError drops to 2.46:1 on the nord panel, while the Mantine token is the one tokens.css already corrected per colour scheme (5.05:1 light, 7.4:1 dark).
- `packages/editor-core/src/components/design-system-panel.tsx`, `keywordsWithVariants`: Fill-blank modes change answer syntax and need question-specific choices.
- `packages/editor-core/src/components/design-system-panel.tsx`, `applyThemePreset`: Palette and pairing changes preserve authored presentation and inheritance.
- `packages/editor-core/src/components/design-system-panel.tsx`, `DesignSystemPanel`: Use the same resolved palette as the accessibility checker so the Design panel reports the colours the checker measures.
- `packages/editor-core/src/components/design-system-panel.tsx`, `sectionAccordion`: Status colours sit in Basic → Colors, alongside the other theme colours, because that is where an author looks after the accessibility checker reports "Success on background contrast ratio is …". Until now the checker named colours the panel had no control for.
- `packages/editor-core/src/components/design-system-panel.tsx`, `STATUS_COLOR_MIN_RATIO`: WCAG 1.4.3 threshold for normal-sized status text, and the same number `checkContrastPairs` requires of the status colours, so the readout below a swatch says exactly what the accessibility checker would say about it.
- `packages/editor-core/src/components/design-system-panel.tsx`, `StatusColorField`: Verdict is carried by the wording and the icon, not by the colour of the text, so it survives greyscale and colour-vision deficiency.
- `packages/editor-core/src/components/panel-chrome/panel-accordion.module.css`, `.header[aria-expanded="false"]`: Section titles stay bold whether open or closed. Collapsed headers used to drop to 400 and a muted colour, so once one section was open its neighbours faded out, exactly when you need to see what comes before and after. The chevron already carries open-versus-closed, so dimming the label only cost scannability.
- `packages/editor-core/src/components/panel-chrome/panel-chrome.css`, `:root`: `--panel-control-border-color` used to alias `--border-subtle`, i.e. the same value as `--panel-divider`, a text input's outline and a hairline rule were the same colour by construction, and neither cleared the 3:1 WCAG 1.4.11 asks of a control boundary. It now aliases `--control-border`, which the theme factory guarantees against every panel surface.
- `packages/editor-core/src/components/panel-chrome/panel-chrome.css`, `.panelChrome *:focus-visible`: `--focus-ring` is the contrast-guaranteed variant of the accent (3:1 against bgPrimary, bgPanel and bgCard); `--panel-accent` is the raw fill and is not held to that ratio, so the panel focus indicator was the only one in the app that could fall under 3:1.
- `packages/editor-core/src/components/panel-chrome/panel-field.module.css`, `.rootRow .label`: A row label names an action; stacked labels identify a field value below.
- `packages/editor-core/src/components/panel-chrome/panel-section.module.css`, `:global([data-panel-content="padded"]) > .root > .divider`: Only expand into padding owned by the shared panel containers.
- `packages/editor-core/src/components/panel-chrome/panel-shell.module.css`, `.header`: `padding-bottom` used to be 0, leaning on `.title`'s own margin for the gap below the header. Panels that pass a `header` node have no such margin, so a control in the header sat flush on the first row of panel content: the Design panel's Reset button touched the "Basic" accordion header with a 0px gap, which reads as a seam and fails WCAG 2.5.8 target spacing (a 24px circle on the 19px-tall Reset button intersects the neighbour below).
- `packages/editor-core/src/components/panel-chrome/panel-shell.module.css`, `.title`: Matches .right-panel-frame__title in the desktop shell: sentence case, not uppercase, so self-headed panels read as peers of Blocks / Design / Publish.
- `packages/editor-core/src/components/panel-chrome/panel-shell.module.css`, `.title:not(:last-child)`: Separates the title from a header node; the header's own padding-bottom carries the gap when the title is the only thing in there.
- `packages/editor-core/src/components/panel-chrome/panel-shell.tsx`, `PanelShellProps`: Panel title. Rendered sentence-case as an h2, matching the desktop right-panel frame headers (Blocks, Design, Publish) so self-headed panels sit at the same level as framed ones.
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: `glossaryPage` survives an archetype change. Do not reset it from a navigation preset with `BOOLEAN_NAV_KEYS`.
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: Default enum-valued navigation keys from the archetype preset, as for boolean navigation keys. Reading the global default table here meant a `slides` course silently resolved `navProgressStyle: "bar"` instead of the preset's `"dots"`, so CourseViewer never rendered ProgressDots at all, the dots were absent from the DOM, not hidden by CSS.
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: Pairing migration reads persisted fields before palette defaults are merged.
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: Remove the retired `showBrandingPill` setting from normalized state. Old .prax files may carry it; later saves must not restore it.
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: Defaults for unset nav keys come from the archetype's preset. Filling sidebar defaults here reads as explicit author overrides downstream and silently cancels `navArchetype` (e.g. frontmatter-only `slides`).
- `packages/editor-core/src/lib/themes/normalize-design-variants.ts`, `normalizeDesignVariants`: Defaults belong to the effective navigation resolver, not authored lesson data. Materializing them here would override course settings on any later design edit.
- `packages/editor-core/src/lib/themes/oklch.ts`, `srgbToApcaY`: APCA-W3 intentionally uses simple 2.4 power-law linearization (not WCAG's IEC 61966-2-1 piecewise function).
- `packages/editor-core/src/lib/themes/resolve-theme.ts`, `deriveSectionPalettes`: Derive section palette colors from a theme's base colors. Each palette is a set of CSS custom properties that override the theme defaults within a <section> element. Text colors are auto-derived to meet WCAG 2.x 4.5:1 contrast ratio against the section background.
- `packages/editor-core/src/lib/themes/resolve-theme.ts`, `deriveSectionBackgroundOklch`: Both base and accent are achromatic, stay achromatic (e.g. Minimal)
- `packages/editor-core/src/lib/themes/resolve-theme.ts`, `deriveSectionSurface`: Use a larger lift for very dark backgrounds to ensure card boundaries are perceptible (target >= 1.3:1 surface-to-background contrast). At low L values, L+0.06 only produces ~1.15:1 due to luminance compression.
- `packages/editor-core/src/styles/editor-tokens.css`, `:root[data-praxity-chrome-theme="light"] [data-praxity-chrome]`: Frame tokens belong to admitted editor chrome, never to course content.
- `packages/editor-core/src/styles/editor.css`, `[data-page-canvas] [data-block-type="button"] .mantine-Button-root`: --praxity-color-* vars are injected on [data-page-canvas] in both edit and preview modes. Map them to Mantine's --button-* vars so buttons reflect the course theme.
- `packages/editor-core/src/styles/editor.css`, `:root` syntax-token aliases: These used to be two hand-tuned oklch palettes gated on `[data-raw-theme]`, an attribute the raw editor computed for itself from Mantine's colour scheme. That scheme never tracked the theme chosen in Settings, so the *light* palette was painted onto a dark editor: `as: image` and `alt:` rendered at 1.91:1 on Dracula and the assessment markers `(x)`/`( )` at 1.53:1. That is the "grammar keys and image links are illegible in the dark theme" report. They are now aliases of the desktop theme's own syntax and category tokens, which `theme-factory.ts` contrast-corrects against `--bg-editor` for all 29 themes and `themes/__tests__/theme-contrast.test.ts` asserts. The four raw-editor category aliases are content → `--category-explain` (blue), flow → `--category-practice` (teal), assessment → `--category-engage` (purple), and interactive → `--category-assess` (orange). The theme factory also defines `categoryStructure`, but these four raw-editor aliases do not use it. Sources: the `--praxity-raw-cat-*` definitions in this stylesheet and `CATEGORY_SEEDS` in `apps/desktop/src/renderer/themes/theme-factory.ts`. The gate is `[data-theme]`, which `use-theme.ts` sets on documentElement and is the single source of truth for light/dark in this app.
- `packages/editor-core/src/styles/editor.css`, `.praxity-raw-editor p:has(.praxity-raw-fold-caret)`: A fold caret is taller than a line of the editor, so two openers on consecutive lines would overlap and neither would have a clear 24x24 target (WCAG 2.5.8). Only the rows that carry a caret are raised to the caret's height, ordinary lines keep the editor's density.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-param-name[data-grammar-category="content"]`: Category tokens already guarantee text contrast; opacity would undo it.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-container-guide`: Dedicated widgets keep container guides independent of heading/gutter badges, which use paragraph pseudo-elements and transforms.
- `packages/editor-core/src/styles/editor.css`, `.tiptap p.praxity-raw-hidden-heading-scope`: `hide: true` on a heading hides its whole semantic section. Repeat the gutter dots on every source line in that section so the editor shows the same scope the learner runtime applies.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-delimiter-unmatched`: Syntax tokens are corrected against this neutral editor surface.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-narration-disclosure:focus-visible`: Overrides the editor's blanket descendant focus reset for this real button.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-fold-caret`: The hit area is 24x24 at 100%, the WCAG 2.5.8 target floor, and was 20x20. Only the hit area grew: the glyph is the same size and still sits 12px into the 32px gutter reserved by `.praxity-raw-editor p`, so it stays lined up with the nesting bars and never reaches the code text. Both sizes are stated against the 14px desktop root like the rest of the raw editor (`.praxity-raw-editor` is 0.929rem), so the caret tracks the text-size setting instead of staying 24px in a gutter that had grown to 128px at 400%. `max()` keeps the target at 24px when that setting scales *down*, where the rem alone would fall to 19px. The box is taller than the 21.5px line it sits on, so two openers on consecutive lines, e.g. `as: card` directly above `as: col`, would have overlapping hit areas and neither could claim a clear 24x24. The rows that carry a caret get the caret's own height instead in the fold-caret row rule; widening the editor's line-height would have cost every author 12% of their vertical screen space to fix a couple of rows.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-fold-summary`: Overrides the editor's blanket descendant focus reset, the same way `.praxity-narration-disclosure` does. Without `!important` this outline lost to `.tiptap *:focus-visible` and the caret was reachable by Tab with no visible focus indicator at all.
- `packages/editor-core/src/styles/editor.css`, `.tiptap .praxity-raw-fold-summary`: Exactly 12px at the 14px desktop root, the app's small-text floor. 0.75rem resolved to 10.5px, below a comfortable desktop minimum.
- `packages/editor-core/src/styles/editor.css`, `[data-reveal-flash]`: Arrival cue for a reveal from another panel (accessibility issue, preview block). Landing somewhere new with no confirmation reads as "did it work?", the flash answers that without a permanent mark. Reduced motion keeps the highlight and drops the fade: the cue is the information, the animation is not.

## Consequences

Preserve these constraints when changing this area. Sources are the named symbols and their explanatory comments at commit bed54f6, before this comment-only change. The [architecture guide](../context/architecture.md) describes ownership. Existing tests remain the behavioural gate; this record adds no new behaviour.
